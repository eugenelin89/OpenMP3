## Intended and delivered behavior

[Kickoff #17](https://github.com/eugenelin89/OpenMP3/issues/17) and
[specification #18](https://github.com/eugenelin89/OpenMP3/issues/18) aimed to make
scan outcomes honest and the top player the single collection transport. A settled
nonempty scan should prepare music silently or become the one pending handoff;
explicit user intent must outrank older work. Native controls and accessibility
must reflect those same states.

The delivered player separates browsing, ready, pending and active snapshots.
Initial navigation is silent; top Play starts the chosen ready track. While A is
active, a new settled B appears as Up Next and replaces A once on natural completion
or explicit Next. Paused Next stays paused. Shuffle applies at consumption, history
resets across collection boundaries, and pending wins over repeat. Explicit track
taps invalidate older scan intent. Removal clears future intent/cache without
discarding the active queue. Exhausted recovery promotes B silently; retryable A
remains resumable. Native presentation shares these rules.

## Differences from the plan

There is no intended feature-scope expansion. Discovered track rows can now be
tapped during an ongoing scan, making Q8's explicit-intent rule usable; folder
switching/removal remains restricted during scanning. ChatGPT explicitly reviewed
this interpretation. Manual Retry uses the clearer “Retry previous track” label
when B is ready and moves B back to pending before restoring A.

Available physical verification is narrower than full V205 acceptance. Mirroring
and owner listening established useful current-build behavior, but actual remotes,
routes, interruptions, VoiceOver speech and legacy compatibility remain open.
The simulated accessibility checks were manual Computer Use observations, not a
new XCUITest suite. No complete-Drive-coverage or production-readiness promise was
delivered. Existing access methods, budgets and platform policy remain unchanged.

## What worked

- The fixed PR #14 baseline `5733652b8cb24f17470f954f54149bf9713b3ce7` avoided
  outdated `main` and preserved the keyboard fix. V201 stayed independently
  reviewable until the planned V205 integration.
- Application-boundary TDD with suspended discovery, deterministic randomness and
  captured audio callbacks exposed races without relying on timing sleeps or live
  network failures. Regressions reproduced important defects before correction.
- Independent Standards and Spec reviews separated style judgment from behavioral
  correctness. Spec review found exhausted readiness and Retry/source contradictions;
  focused rechecks verified corrections. Standards suggested consolidating ordering,
  which removed a small duplication without broad refactoring.
- A real small-screen simulator found layout defects absent from core tests. The
  signed build and physical iPhone then exercised discovery and handoffs with live
  data. The owner's listening confirmation filled a gap the tools could not.
- Aggregate-only live evidence preserved useful request/count/timing facts without
  publishing private fixture links, saved names or music metadata.

## Rework, delays and integration

The first ready implementation treated a nonnil current item as resumable even
after permanent exhaustion. A targeted regression required a stronger predicate.
Repeated Drive file IDs across queues exposed why file identity alone cannot reject
old callbacks; generation tokens and per-load callback capture fixed that race.
The recovery implementation initially allowed Retry to play A while showing Ready
B; moving B back to pending restored one coherent source of playback intent.

Largest accessibility text revealed truncation and split status text. Wrapping and
stacking solved the observed layout, followed by keyboard/Done verification. The
V201 integration conflicted in root removal and build-script fixture selection;
resolution retained typed scan status plus intent invalidation and made fixture
flags mutually exclusive. Tests migrated from old string outcomes to typed values.

An initial test assertion indexed an empty array and crashed; it was corrected to
inspect `first`, and the crash was never counted as a passing test. Signing and
installation succeeded with existing credentials; a locked-device launch attempt
required Mirroring/Spotlight recovery. Initial automatic approval reviews rejected
push/network attempts; retries supported by the user's explicit publication and
fixture authorization succeeded. No blocker remains from those attempts.

## Verification and residual risk

The final code passed **55 XCTest cases**, normal/player-fixture/scan-fixture
simulator builds and a signed device build. Simulator iOS 26.5 checks covered
largest accessibility text, title/status wrapping, reachable controls and mode
values, visible URL entry, and actual software-keyboard dismissal with Done.
Simulator text size was restored afterward.

The installed iPhone 16 on iOS 26.5.2 ran app 0.2/build 2. Observations covered silent
cold launch, A/B discovery, silent ready Next, top Play, A continuing during B scan,
Pause/Play retention, explicit handoff, a separate natural handoff, paused Next,
background timing, mode selection and continuation within B. The natural boundary
was established by before/after observations with no intervening Next/seek; its
exact instant was not captured. Maps reached onboarding only, so no navigation
prompt was tested. The owner confirmed general audibility on this installed build.

Actual lock-screen/Control Center/headset command delivery and displayed metadata,
Bluetooth/route changes, interruptions, Maps prompts, spoken VoiceOver, extended
background reliability, per-transition audible continuity and older devices are
**Not tested / require owner verification**. Shared metadata tests cannot substitute
for these. No current-build physical recovery-exhaustion experiment is claimed.

The anonymous live probe found 14 tracks in one folder with two HTTP 200 responses,
zero retries and about 5.49 seconds; it certifies neither coverage nor budgets.
T01's undocumented-page parsing, pagination/resource-key behavior, representative
large/non-audio/negative fixtures, independent completeness manifests and measured
budget justification remain unresolved. App limitations and unknown coverage must
stay visible in any distribution or acceptance decision.

## Environment improvements, in priority order

1. **Automated checks — high:** `Package.swift` provides `swift test`; scripts provide
   simulator builds, but inspection found no CI workflow, configured hooks path or
   active Git hooks (only sample hooks). Wire the existing tests and normal/fixture
   builds into CI. Add a focused software-keyboard/largest-text UI regression; core
   tests did not detect visual obstruction. This is a missing guardrail, not a need
   for another prose coding rule. No CI service configuration was added in this
   retrospective's documentation-only scope.
2. **Information access — high:** prepare authorized fixtures with expected manifests
   for paging, resource keys, restricted descendants and non-audio-heavy trees.
   Prepare an owner-run remote/route/VoiceOver checklist tied to the exact build.
   Audio observations need a listener; a screen recording alone is insufficient.
3. **Navigation — medium:** keep a short index linking the active spec, ticket graph,
   fixed baseline and latest evidence. This report's branch table supplies the
   current-cycle map; use a small navigation pointer if future runs repeatedly
   rediscover it. No applicable repository/ancestor `AGENTS.md` was found, so adding
   a large instruction file would add context without solving a demonstrated need.
4. **Review judgment — medium:** ask reviewers to evaluate resumability separately
   from item existence and distinguish future intent from active output. Preserve
   the application-boundary regressions as executable rules. No missed mechanical
   standards violation was found that warrants a new syntactic lint rule.
5. **Tool economy — medium:** pin base/head per review; inspect bounded output and
   batch independent reads/builds. Read current UI state before acting, and separate
   animation frames from settled results. Attach evidence to the tested code SHA
   so documentation updates do not trigger needless rebuilds.
6. **Global steering and no-ops — low:** no repository steering document needed
   pruning in this run. Keep policy in canonical references and avoid repeating
   budget/platform values in new always-loaded instructions. There is no evidence
   here supporting changes to the user's global agent configuration.
