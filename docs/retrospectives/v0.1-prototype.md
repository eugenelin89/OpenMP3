## Workflow: what worked and what failed

- **`/grill-with-docs`:** explicit decisions and domain vocabulary separated
  selected root from queue source, clarified recovery/ordering, and kept optional
  playlists out of the core. The later no-key-only decision was recorded rather
  than silently using the earlier developer-key fallback.
- **`/to-spec`:** [specification #3](https://github.com/eugenelin89/OpenMP3/issues/3)
  established one application-level test boundary. This supported behavioral
  regression tests without binding them to private implementation details.
- **`/to-tickets`:** dependency-ordered vertical slices made T01 feasibility and
  integrated-device acceptance distinct. Owner-authorized provisional development
  was recorded separately from evidence that a gate had passed.
- **`/implement` and review:** reproducible probes, aggregate-only public evidence,
  and independent Standards/Spec reviews caught real defects in empty-folder
  parsing, recovery position, shuffle boundaries and playback history. Fixes gained
  targeted regressions. Stacked PRs kept the keyboard fix independently reviewable.
- **Physical acceptance:** the owner exposed a primary-flow defect that passing
  core tests and builds missed: the fixed player consumed the keyboard-reduced
  viewport, hiding URL entry. Reproduction on a small simulator preceded the fix:
  one scrollable layout, explicit focus scrolling and Done. The lesson is to test
  the first useful action with the software keyboard early, on a small viewport.
- **Evidence maintenance:** owner confirmation arrived after the initial report,
  leaving “unverified” summaries stale until reconciled. Repeated reviews and long
  tool outputs also consumed attention. A dated evidence update and an explicit
  iteration stop decision prevent completed work from cycling back into review.

## Accepted risks for a future iteration

T01 remains technically incomplete: undocumented webpage parsing, real pagination
and resource-key coverage, representative large/non-audio-heavy and negative
fixtures, independent completeness manifests, and live retry/restriction behavior
are unresolved. Measured application scan budgets remain provisional; values and
rationale stay only in the [canonical scan-limits section](../../Drive_Folder_Music_Player_Brainstorm.md#v01-recursive-scan-boundary-and-limits).

Comprehensive current-build Maps/lock-screen/remotes/route-change/interruption
behavior, per-stage audibility, VoiceOver, full accessibility coverage and legacy
runtime/hardware compatibility remain unverified or partial. The
[canonical platform baseline](../../Drive_Folder_Music_Player_Brainstorm.md#platform-compatibility-baseline-single-source-of-truth)
is unchanged. These risks are accepted for this experimental iteration, not waived
for a future reliability or distribution promise. Playlists, billing and store
distribution remain deferred.

## Environment improvements, in priority order

1. **Automated checks:** wire the existing `swift test` and simulator-build commands
   into CI. Inspection found no CI workflow or active Git hook running them. Add a
   focused software-keyboard/small-viewport UI regression and a mid-edit text-size
   change case; application tests cannot detect visual obstruction. Use executable
   checks for mechanical rules rather than adding prose standards.
2. **Information access:** prepare authorized fixtures with expected manifests
   before the next Drive experiment. Include paging, keys and negative cases;
   preserve aggregate-only publishing. Settle the no-key completeness promise
   before expanding features, without introducing another access method implicitly.
3. **Navigation and evidence:** add a short navigation pointer to canonical policy,
   active spec/tickets, branch relationships and latest evidence. No applicable
   `AGENTS.md` was found; avoid creating a large instruction file. Reconcile dated
   owner confirmations into the evidence summary as soon as they arrive.
4. **Review judgment:** require reviewers to distinguish build/test success,
   visual usability, native events and human listening evidence. Review the actual
   first-run flow and enlarged-text behavior, not only static view code.
5. **Tool economy and stopping:** pin the review base/head once, use focused file
   and UI observations, and rerun checks only after relevant changes. End an
   accepted iteration with one risk register; reopen work only under a new scope.

Recommendations only: no new implementation, checks, fixtures or policy files
were added by this retrospective.
